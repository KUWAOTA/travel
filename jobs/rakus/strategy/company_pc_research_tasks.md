# ラクス応募 会社PCで確認する残課題

更新日: 2026-07-13

## 1. このファイルの使い方

本人への聞き取りで、経歴・担当範囲・技術構成の大部分は確認できた。このファイルでは、会社PC上の記録を見なければ確定できない事実だけを確認する。

各項目で書くのは、次の4点だけでよい。

1. 確認した事実
2. 根拠の種類（チケット、リリース履歴、JaCoCoレポート、予定表等）
3. 実績／目標／予定／推定の区分
4. 職務経歴書に書ける一般化した一文

コード、設計書、画面、社内URL、チケット本文、顧客名、ログ実値はコピーしない。社内固有名詞は一般化し、数字は外部説明可能な集計値だけ記録する。

## 3. 最優先: 30分で確認する項目

### P0-1. v1.2～v1.4の年月

#### 会社PCで見る場所

- リリース履歴
- 対象バージョンの最初と最後のチケット
- リリース予定表

#### 確認して書くこと

次の表だけを埋める。日付は月単位でよい。

| バージョン | 開発開始 | リリース | 終了 | 実績／予定 | 根拠の種類 |
| --- | --- | --- | --- | --- | --- |
| v1.2 自動検品 | 2024-10頃（仮） | 2025-10頃（仮） |  | 実績 |  |
| v1.3 追加機能 | 2025-12頃（仮） | 2026-04頃（仮） |  | 実績 |  |
| v1.4 追加要件 |  | 2026-09予定 |  | 予定 |  |

#### どこまで確認すれば終了か

- v1.2とv1.3のリリース月が確定する。
- v1.4は「2026年9月予定」であることを予定表から確認する。
- バージョンごとの細かな機能一覧は作らない。

### P0-2. 単体テスト施策の実測値

#### 会社PCで見る場所

- 現存するJaCoCoレポート
- 単体テストの対象コード
- テスト作成How To

#### 確認して書くこと

```text
レポートの時期:
対象範囲の一般名: 検品機能のうち問題が起きやすい一部メソッド群
対象にした本番コード側のメソッド数: 約40（要確認）
C0実測値:
C1実測値:
80％以上を達成した範囲:
How Toに含まれる内容: 環境構築／テスト設計／実行／カバレッジ確認
現在の利用状況: 利用停止。他の改善を優先
```

#### どこまで確認すれば終了か

- 「約40件のテスト」ではなく「約40メソッドを対象」が正しいと確認する。
- システム全体の80％ではなく、限定範囲の実績値をC0／C1別に記録する。
- レポートやコードを持ち出さない。

### P0-3. 非同期処理・接続競合のチケット

次の3件を別々に確認する。

1. v1.2で、5～6段のコールバックをElemental2 Promiseの`then`へ整理した対応。
2. F5更新時、切断途中にCoreが「既存接続あり」と誤判定する問題に対し、画面終了時に接続を切らないよう変更した対応。
3. Core側の`disconnect`完了前に共通アプリ側の`start`が走る問題に対し、`start`／`stop`の完了待ちを入れた対応。

#### 各チケットで書くこと

```text
対象バージョン:
対応年月:
症状:
原因:
変更:
本人が行った確認:
単体テスト:
結合テスト:
実機システムテストの担当者:
リリース後の再発有無:
根拠の種類:
```

#### どこまで確認すれば終了か

- 3件を混同せず、それぞれ「原因→変更→確認結果」を1～2文で説明できる。
- デッドロックと断定しない。実態は非同期処理の順序競合として記録する。
- 別のデッドロック事例は、具体的なチケットを見つけた場合だけ追加する。

### P0-4. v1.3状態管理設計の数字

#### 確認して書くこと

```text
対象: RFIDタグ発行・照合画面
変更前の画面クラス行数: 約3,000行（要確認）
別クラスへ分離した行数: 約300行（要確認）
新設したクラス数:
主な状態: 発行待ち／発行中／発行完了／照合待ち／照合中／照合完了（要確認）
利用した構造: ViewState／状態別クラス／Strategy
結合テストで確認した主な組合せ:
リリース後に同種の状態不整合が発生したか:
```

#### どこまで確認すれば終了か

- 全面刷新ではなく、既存影響を避けて約300行を段階的に分離した事実を確認する。
- 「不具合を完全防止」ではなく、現時点で把握している再発有無を書く。

## 4. 次点: 追加30～45分で確認する項目

### P1-1. 保全部品管理案件のフローチャート

#### 確認して書くこと

```text
正式な選択階層の一般名:
権限による違い:
保全／保全外による違い:
原価種別による違い:
初回に見落とした例外を1件:
PM経由で保全部門へ確認した回数: 約3往復（要確認）
フローを受けて実際に変えた分岐を1件:
次版へ持ち越した選択ロジック:
2025-11～2026-02に行ったクラス構造変更:
3部門6名で確認した事実:
```

#### どこまで確認すれば終了か

- 初回に例外を可視化できた一方、クラス構造変更を次版へ持ち越した事実も書く。
- 「手戻りゼロ」「仕様漏れを完全防止」とは書かない。
- 情シスが持っていた既存フローチャートの存在を踏まえ、「既存業務資料を早期確認する必要性を学んだ」と整理する。

### P1-2. イタリア子会社との技術対話

#### 確認して書くこと

```text
期間: 2026年2月頃、約2週間
相手: Core担当のイタリア子会社技術者
英語で確認したこと: 更新影響／DBマイグレーション／DBスナップショット復旧
本人が実施した作業:
日本側MTGで共有した日または回数:
現在整備中の共有方法:
```

#### どこまで確認すれば終了か

- 英語で設計交渉したとは膨らませず、技術確認と実作業を3文で説明できる。
- 「標準手順を確立」とは書かず、共有方法は整備中とする。

### P1-3. エンジニア道場の記録

#### 既知の数字

- 2025年11月～2026年1月。
- 新入社員1名、3サイクル。
- 1サイクル約2週間、1テーマ内に約5課題。
- 修正ラリーを含め1サイクル約5～10回、合計約25回レビュー。
- 1回約15～60分。
- 3サイクル目は先輩開発メンバー5名全員にもレビューを依頼。

#### 会社PCで確認すること

- カレンダーや課題記録から、3サイクルの実施時期と概算回数に大きな誤りがないか。
- 代表的な指摘を2～3件確認する。候補は命名、プリミティブ型の選択理由、イミュータブル設計、税率をメンバー変数にした理由。
- 受講者コメントの要旨を確認する。「先輩の指摘意図が分かるようになった」「開発の基礎になった」。

#### どこまで確認すれば終了か

- 本人観察と受講者コメントを分ける。
- 逐語引用できない場合は「～という趣旨のコメント」とする。

### P1-4. AI並行調査の実績値

#### 会社PCで見る場所

- 当時本人が残した週次集計
- v1.2／v1.3のシステムテスト不具合記録

#### 確認して書くこと

```text
v1.2の集計週:
本人が1週間で対応したシステムテスト不具合: 9件
v1.3の集計週:
本人が1週間で対応したシステムテスト不具合: 26件
3並行調査の方法: 異なる仮説を3チャットへ依頼し、人間が比較・検証
主なツール: GitHub Copilot Enterprise
AI出力の有用率: 約7割（本人概算）
300回以上の意味: 約1年半のAI調査依頼回数の概算
```

#### どこまで確認すれば終了か

- 9件・26件が各1週間、同じ「システムテストで検出されたバグ修正」の集計であることを確認する。
- バージョン間で難度が同一ではないため、「AIで生産性が3倍になった」と断定しない。
- チーム展開はコンセプト合意・準備中であり、標準化済みとは書かない。

## 5. 余力がある場合だけ確認する項目

### P2-1. 技術構成のバージョン

以下は構成として確認済み。職務経歴書に必要な場合だけ正確なバージョンを確認する。

- Java／JDK
- Android SDK 33
- Smart GWT／GWT 2.12.2
- Dropwizard（Jetty、Jersey、Jackson、Hibernate）
- MySQL 8
- Gradle
- Windows Server
- GWT RPC、Jersey REST API
- 定期実行のCSV取込バッチ

確認するのはJDK、Dropwizard等のバージョンだけ。内部モジュール名や構成図は持ち出さない。

### P2-2. Git導入状況

```text
PifaaでGitHubを使用した期間: 2022-10～2024-03
PifaaのPRレビュー: なし
id-BridgeでSVNを使用した期間: 2024-04～現在
Git導入を始めた年月:
Gitへ移す対象:
導入目的:
PRレビューを始める予定の有無:
```

通常案件の定常レビューがない事実はそのまま扱い、PRレビュー経験を誇張しない。

### P2-3. PoCの代表例

- id-Bridge: 未対応のRFIDリーダー／ライターで検品できるかを試作。
- Pifaa: バス位置情報をGoogle Maps上へ表示する試作。

各例について、期間、本人の担当、顧客要望、試したこと、結果を各1行で書ける場合だけ職務経歴書へ使う。正式なAgile経験とは表現しない。

## 7. 終了基準

- P0完了: v1.2～v1.4の年月、JaCoCo実測値、非同期処理3件、v1.3状態管理の数字が確定する。
- P1完了: フローチャート、海外技術対話、育成、AI活用を、誇張なしで各3～5文にできる。
- P2は未完でも応募書類を作成できる。確認に時間がかかる場合は打ち切る。
